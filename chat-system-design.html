Chapter 00

Framing the problem before touching a keyboard

Every good system design starts by refusing to design anything yet. The single most common failure in this exercise — in interviews and in real life — is jumping to WebSockets and Kafka before anyone has said what the system must actually do. So we pin down scope, then requirements, then the numbers.

"A chat application" hides at least three very different systems, and they scale in different ways. Be explicit about which you mean, because it changes almost every downstream decision.

FlavorExampleHardest part
Human ↔ humanWhatsApp, Slack, DiscordFan-out & presence — one message to many connections, delivery guarantees, ordering
Human ↔ AIChatGPT, Claude webThe inference layer — GPU fleets, token streaming, batching, cost per request
BothAI copilots inside team chatAll of the above, plus routing between the two paths

Your goal — "something like the web version of ChatGPT" — is squarely the human ↔ AI case, but at planet scale it inherits nearly every hard problem of the human-to-human case too: millions of persistent connections, real-time streaming, presence, history, multi-region. So we build the general real-time substrate first (L0–L5, L7), then bolt on the part that makes it ChatGPT rather than Slack — the inference layer (L6).

Functional requirements

What the system must let a user do. Keep this list short and ruthless; everything you add here you must later scale.

  • Send a message and get a streamed response, token by token, with low time-to-first-token.
  • Maintain conversations — ordered history, persisted, retrievable, editable/branchable.
  • Multi-device: start on a phone, continue on a laptop, see the same state.
  • Stop generation mid-stream; regenerate; edit a previous turn.
  • Attachments (images, files) and, later, multimodal in/out.

Non-functional requirements (the ones that actually cost money)

These are the requirements you defend in design review. Attach a number and a percentile to each — "fast" is not a requirement, "p99 time-to-first-token < 800ms" is.

The tradeoff triangle

Latency, consistency, and cost pull against each other. Strong global consistency raises latency and cost; ultra-low latency usually means relaxing consistency (eventual delivery, at-least-once) and spending on redundancy. Every level below is really a decision about where on this triangle you're willing to sit for a given feature.

Chapter 01

Back-of-the-envelope: what does "1M req/s" actually demand?

Numbers turn hand-waving into engineering. Before designing, we size the system so every later choice has a target to hit. The point isn't precision — it's discovering the order of magnitude, and where the pain will be.

Traffic assumptions

Say we want a system that peaks at 1,000,000 chat messages per second. We work outward from there.

QuantityAssumptionResult
Peak message send rategiven1,000,000 / s
Daily active users (DAU)~20 msgs/user/day, peak = 5× average~430M DAU
Concurrent open connections~5% of DAU online at peak~20M sockets
Connections per server~100k WebSockets/box (tuned Linux)~200 conn servers
Avg response length~500 output tokens—
Token generation load1M req/s × 500 tok5×10⁸ tok/s
Where the math breaks reality

That token rate is the number that separates "big web app" from "you now run one of the largest GPU fleets on Earth." At ~2,500 output tokens/sec per high-end GPU with good batching, 5×10⁸ tok/s implies on the order of hundreds of thousands of GPUs for generation alone. This is why no real product is uniformly at 1M req/s of LLM inference — it would cost billions per year. The realistic target is a system whose architecture scales to that shape, provisioned to actual demand. We design for the shape; we pay for the load.

Storage sizing

Each message ≈ 1 KB of text + metadata. At 1M/s that's ~1 GB/s of raw writes, ~86 TB/day, ~31 PB/year before replication and indexes. This immediately kills any single-database design and forces sharding (L5). It also tells you cold storage tiering isn't optional — most conversations are read once and never again.

Bandwidth

Streaming 500 tokens as ~4 chars each over SSE/WebSocket framing ≈ a few KB per response. At 1M/s that's single-digit GB/s egress from the app tier — meaningful, but dwarfed by media attachments. Images/files, not text, dominate your CDN and egress bill.

These four numbers are your compass. Notice the asymmetry: connections and storage are a solved, cheap problem at this scale; GPU inference is the cost center. That reshapes the whole project — most of the interesting engineering in an LLM chat product is spent making each GPU-second go further.

L0 · The monolith

One box, one process, and a to-do app with delusions

Every system starts here, and you should be able to draw it in ten seconds. A single server runs the web app, the business logic, and an embedded or co-located database. It handles maybe hundreds of concurrent users. This is not an embarrassment — it's the correct starting point, and it defines the contract every later level must preserve.

The data model that survives forever

Get this right and it barely changes through every later level. Three core entities:

  • users — id, auth identity, profile.
  • conversations — id, owner, title, created_at. (In group chat: a channels/rooms table plus a membership join table.)
  • messages — id, conversation_id, author (user or "assistant"), content, created_at, and a monotonic sequence number scoped to the conversation.
Design once, keep forever

The per-conversation sequence number is the most important early decision. It gives you stable ordering independent of wall-clock time (clocks skew across servers), enables "give me everything after message N" sync, and becomes the anchor for pagination, read receipts, and conflict resolution later. Add it at L0 even though you don't need it yet.

Why you leave L0

The moment two things are true — you can't afford downtime for deploys, and one machine can't hold the load — L0 is finished. Not before. Premature distribution is how projects die of complexity before they ever get users.

Capability envelope

Handles

~hundreds to ~1,000 concurrent users; a few hundred req/s of light CRUD on one well-tuned box.

Breaks when

Traffic saturates the box, or you can no longer accept downtime for deploys/restarts. A single crash = total outage.

Can't do

High availability, zero-downtime deploys, horizontal scale, or real server-push at scale. App and DB fight for the same CPU/RAM.

Improve in place first

Vertical scale (bigger box), DB indexes, connection pooling, a query cache, gzip. Squeeze this before distributing anything.

Trigger → L1You need to deploy or restart without dropping users, or one machine is the bottleneck.
L1 · Stateless app + real database

Split the tiers so you can restart without fear

The first real architectural move isn't adding servers — it's making one server replaceable. We separate the stateless application tier from the stateful data tier, and we push all session state out of process. Now any app instance can die or deploy without losing anything.

The golden rule: app servers hold no state

No user sessions in memory, no uploaded files on local disk, no "sticky" anything (yet). Everything that must survive a restart lives in a shared, external system:

StateWhere it goesWhy
Session / authSigned token (JWT) or Redis session storeAny server can validate any request
Messages & conversationsPrimary databaseDurability, shared read/write
Uploaded filesObject storage (S3 / GCS)Local disk dies with the box
Hot lookups, countersRedis / MemcachedOffload the DB, sub-ms reads

Read scaling: replicas and cache

Chat is read-heavy (you re-open conversations far more than you send). Two cheap wins before any hard sharding:

  • Read replicas — the primary handles writes; replicas serve reads. Beware replication lag: a user who just sent a message may hit a replica that hasn't seen it. Fix with "read-your-writes" routing (send that user's reads to the primary briefly) or read from cache.
  • Cache-aside — recent messages and conversation lists in Redis. On write, update the DB then invalidate/update the cache. This is where cache invalidation — famously one of the two hard problems — starts to bite.
Gotcha: the dual-write trap

Writing to the database and the cache (or search index, or another service) in the same request is a distributed transaction in disguise. If the second write fails, your systems disagree. Prefer a single source of truth plus asynchronous propagation — write to the DB, emit an event, let consumers update caches/indexes. This "log then derive" pattern (Change Data Capture) reappears everywhere at scale.

Capability envelope

Handles

~tens of thousands of users; reads scale wide via replicas + cache. Deploys are now safe — instances are disposable.

Breaks when

Write volume hits the single primary's ceiling (~a few thousand writes/s), or replication lag makes reads visibly stale.

Can't do

Real-time server push (still request/response), one write master, cache-invalidation correctness gets fiddly.

Improve in place first

Read replicas, cache-aside, CDN for assets, PgBouncer pooling, read-your-writes routing, bigger primary.

Gain over L0 High availability and zero-downtime deploys — the app tier is now cattle, not a pet.
Trigger → L2You need the server to push — stream an answer token-by-token, or deliver a message the instant it arrives.
L2 · Real-time transport

How does the server push, instead of the client asking?

HTTP is a client-asks / server-answers protocol. Chat needs the opposite: the server must push a new message — or the next streamed token — the instant it exists. This is the defining technical choice of any chat system, and for LLM chat specifically it's the difference between watching an answer appear word by word and staring at a spinner.

The four transports, from worst to best fit

TechniqueHowGood forCost
Short pollingClient asks "anything new?" every N secondsPrototypes onlyWasteful, laggy, hammers the DB
Long pollingServer holds the request open until there's dataFallback pathConnection churn, awkward
SSE (Server-Sent Events)One long-lived HTTP stream, server → client onlyLLM token streamingOne-directional; simple, HTTP-native, auto-reconnect
WebSocketFull-duplex persistent TCP connectionGroup chat, presence, typingStateful; needs its own infra
The choice ChatGPT-style products actually make

For a human ↔ AI product, the dominant real-time need is streaming one long answer from server to client — which is exactly what SSE was built for. It rides on plain HTTP/2, passes through proxies and load balancers cleanly, reconnects automatically, and needs no special socket infrastructure. Many LLM chat frontends use SSE for the response stream and ordinary HTTP POST to send the prompt. WebSockets earn their keep once you add bidirectional, low-latency features (multi-user rooms, presence, collaborative editing). Plenty of large systems run both: SSE for the AI stream, WebSockets for interactive/social features.

Token streaming, concretely

The user POSTs a prompt. The server opens an SSE stream, calls the model, and forwards each generated token as an event the moment it arrives. The frontend appends tokens to the bubble as they land. Key details that make it feel good:

  • Flush immediately — disable response buffering (Nginx proxy_buffering off) or tokens arrive in clumps.
  • Heartbeats — send a comment/ping every ~15s so intermediaries don't kill an "idle" stream.
  • Cancellation — when the user hits Stop, the client aborts the request; the server must propagate that to the model to free the GPU. Un-cancelled streams are pure wasted money.
  • Resumability — include a stream/message id and last-event-id so a dropped connection can resume rather than restart the (expensive) generation.

Capability envelope

Handles

Real-time streaming to thousands of concurrent open streams on a single connection-capable server; feels instant.

Breaks when

One box hits its socket/CPU/file-descriptor ceiling, or a deploy drops every live stream at once.

Can't do

Deliver between users on different servers (there's only one here), or survive that server dying.

Improve in place first

Raise OS limits (fds, ephemeral ports, TCP backlog), disable proxy buffering, add heartbeats, compression, backpressure.

Gain over L1 The server can push — token streaming and instant delivery become possible.
Trigger → L3One server can't hold all the connections/load; you need a fleet behind one address.
L3 · Horizontal scale & load balancing

Many app servers behind one address

One box can't hold the load, so we run many identical stateless app servers and put a load balancer in front. Simple in principle — but persistent connections (SSE/WebSocket) break several assumptions that request/response load balancing takes for granted.

Layers of load balancing

  • DNS / anycast — spreads users across regions and edge points of presence.
  • L4 (transport) LB — routes by IP/port, cheap, connection-aware; good for raw TCP/WebSocket throughput.
  • L7 (application) LB — understands HTTP: path routing, TLS termination, retries, header-based routing. Where most policy lives.

Common algorithms: round-robin (default), least-connections (better for long-lived sockets — you want to avoid piling new connections on a box that's already saturated), and consistent hashing (route a given key to a stable server; crucial at L4).

The persistent-connection problem

A WebSocket lives for minutes or hours. Standard load balancing assumes short requests it can freely re-route; here it can't. Three consequences: (1) connection draining — during a deploy you must let existing sockets finish or migrate rather than hard-cutting them; (2) imbalance — least-connections matters far more than round-robin; (3) the server holding your socket is now, temporarily, stateful about you — it knows you're connected. That last point is the whole reason L4 exists.

Sticky sessions: a tempting trap

You can pin a user to one server ("sticky sessions" via a cookie or IP hash). It makes local caching easy — and it makes deploys, failures, and rebalancing painful, because that server now holds irreplaceable state. The modern preference: keep app servers stateless and solve "which server holds this user's socket?" with a shared registry, not stickiness. That question — routing a message to the right connection when connections are spread across 200 servers — is exactly what the next level exists to answer.

Capability envelope

Handles

~100k–1M+ concurrent connections across the fleet (~100k/box × N); horizontal scale for stateless work.

Breaks when

Two users on different servers must talk — no server can reach another's sockets. Deploys risk mass disconnects.

Can't do

Cross-server message delivery, multi-device sync, or presence — every server is an island.

Improve in place first

Least-connections balancing, connection draining, autoscaling on connection count, health checks, jittered reconnect.

Gain over L2 Capacity scales by adding boxes; no single server is a ceiling anymore.
Trigger → L4Any feature that spans servers — group chat, multi-device, presence — needs cross-server delivery.
L4 · The fan-out problem

The hardest problem in real-time chat

Alice's socket is on connection-server 7. Bob's is on server 142. Alice sends a message to a room Bob is in. Server 7 received it — but server 7 has no TCP connection to Bob. How does the message cross the gap? This routing problem, at millions of connections, is the core of every real-time chat backend.

The architecture: connection tier + pub/sub backbone

Split the app tier in two. Connection servers (a.k.a. gateway / edge) do exactly one job: hold sockets and shuttle bytes. Behind them, a pub/sub or message backbone decouples "who received it" from "who needs it."

How the message finds Bob

  1. Server 7 receives Alice's message, assigns it a sequence number, and persists it (durability first).
  2. Server 7 publishes it to the channel for that room/conversation.
  3. Every connection server subscribed to that channel — including 142 — receives it.
  4. Server 142 looks up its local table of "which of my sockets belong to this room" and writes the bytes to Bob.

No server needs to know the global map of every socket. Each knows only its own sockets plus which channels to subscribe to. The backbone does the crossing.

Redis Pub/Sub vs. a real message queue

Redis Pub/SubKafka / log-based queue
DeliveryFire-and-forget (at-most-once)Durable, replayable (at-least-once)
If a consumer is downMessage is lostRead it later from the log
LatencySub-millisecondLow, but higher than Redis
Use it forLive fan-out to online socketsDurable pipeline, async workers, CDC, analytics
Real systems use both

A common pattern: persist to the DB (source of truth) → publish to Redis for instant delivery to online users → also write to a durable log/queue for offline delivery, push notifications, search indexing, and analytics. Online users get sub-ms delivery; offline users get the message on reconnect via a "give me everything after sequence N" sync against the DB. This is why the sequence number from L0 matters so much.

Presence and the "which server holds this socket?" registry

Presence (who's online, typing indicators, read receipts) is deceptively expensive — it's high-write, low-value-per-write, and fans out constantly. Keep it in a fast ephemeral store (Redis with TTLs), debounce updates, and never persist typing indicators. A connection registry (user → connection server) also lives here, refreshed by heartbeats so dead servers' entries expire automatically.

Capability envelope

Handles

Millions of connections with correct cross-server delivery, group fan-out, multi-device sync, and presence.

Breaks when

A hot channel overwhelms the backbone, or plain Redis pub/sub drops messages for a briefly-down consumer.

Can't do

Durably store PB-scale history on the backbone, or guarantee offline delivery without the DB behind it.

Improve in place first

Hybrid path (persist → Redis → durable log), channel sharding, presence debounce, at-least-once + dedup by message id.

Gain over L3 Any user reaches any other user regardless of which server holds their socket — real chat is now possible.
Trigger → L5The single database can't hold the write throughput or the petabytes of accumulating history.
L5 · Data at scale

When one database is no longer a database

At 31 PB/year and 1 GB/s of writes, a single primary is impossible. We shard. But how you shard determines which queries stay fast and which become distributed nightmares — so we pick the shard key by studying the access pattern, not the data.

Choosing the shard key

Chat's dominant access pattern is "load all messages in this conversation, in order." So shard by conversation_id. Every message in a conversation lives on one shard; loading a conversation hits exactly one shard; the sequence number gives order within it. Sharding by user_id instead would scatter a group conversation's messages across many shards — a fan-in read on every open.

Gotcha: hot partitions

A viral group, a celebrity's channel, or a runaway AI agent can make one shard take vastly more traffic than the rest — a "hot partition." Consistent-hash sharding alone won't save you. Mitigations: split the hot conversation across sub-shards by time window, add a caching layer in front, and rate-limit pathological producers. Design for the assumption that load is never uniform.

Right database for the right job (polyglot persistence)

DataStoreWhy
Messages (append-heavy, time-ordered)Cassandra / ScyllaDB / DynamoDBWide-column, linear write scaling, tunable consistency, TTL for tiering
Users, conversations, billingPostgres / sharded relationalTransactions, relations, correctness
Hot cache, presence, countersRedisSub-ms, ephemeral
Full-text / semantic searchElasticsearch / vector DBSearch over history; retrieval for AI context
AttachmentsObject storage + CDNCheap, durable, edge-cached
Event pipelineKafkaCDC, analytics, async work

Hot vs. cold: tier aggressively

Access to message history is extremely skewed — recent messages are read constantly, old ones almost never. Keep the last ~30 days in the fast tier; age the rest to cheaper columnar/cold storage. For an AI product this also feeds retrieval: long conversations and knowledge bases are embedded into a vector store so the model can pull relevant context without stuffing everything into the prompt.

Capability envelope

Handles

PB-scale storage and ~1 GB/s of writes via horizontal sharding; the right store for each data shape.

Breaks when

A hot partition (viral room, runaway agent) overwhelms one shard while the rest sit idle.

Can't do

Cheap strong global consistency, easy cross-shard transactions, or painless rebalancing.

Improve in place first

Shard by conversation_id, sub-shard hot keys by time window, cache in front, hot/cold tiering, CDC pipeline.

Gain over L4 Storage and write throughput scale linearly — history is no longer a ceiling.
Trigger → L6You add AI generation — now the bottleneck moves from data to GPUs.
L6 · The LLM inference layer

The part that makes it ChatGPT, not Slack

Everything so far applies to any real-time chat. This level is what a human ↔ AI product adds — and it dominates the cost, the latency budget, and the operational difficulty. Serving an LLM is not like serving an API; it's running a fleet of extremely expensive, stateful, latency-sensitive accelerators as efficiently as physics allows.

The request path, end to end

Context assembly & the token budget

Before the model runs, you build its input: the system prompt, relevant conversation history (often summarized or retrieved rather than sent whole), retrieved documents (RAG), and the new user turn — all inside a fixed context window. Every token here costs money and latency, so this stage is an optimization problem: send the model exactly what it needs and nothing more. Prompt caching (reusing the computed state of a stable prefix like the system prompt) is one of the biggest cost levers available.

Why serving an LLM is hard: the two phases

PhaseWhat happensBottleneck
PrefillProcess the whole prompt at once, fill the KV cacheCompute-bound; sets time-to-first-token
DecodeGenerate one token at a time, autoregressivelyMemory-bandwidth-bound; sets tokens/sec

These two phases stress the GPU differently, which is why modern serving stacks sometimes disaggregate them onto different hardware pools. The KV cache — the model's memory of the tokens so far — grows with context length and eats GPU memory (HBM), which caps how many requests fit on a card at once.

The efficiency levers (this is where the money is)

  • Continuous batching — instead of waiting to assemble a fixed batch, the server continuously slots new requests into the running batch as others finish. This is the single biggest throughput win; it can multiply GPU utilization several-fold.
  • PagedAttention / KV-cache paging — manage KV memory in pages (like OS virtual memory) so you don't over-reserve, fitting far more concurrent requests per GPU.
  • Quantization — run weights at lower precision (FP8/INT8/INT4) for more throughput per card, trading a little quality.
  • Speculative decoding — a small draft model proposes several tokens; the big model verifies them in one pass, cutting latency.
  • Model routing — send easy queries to a small/cheap model and hard ones to the flagship. Most traffic doesn't need the biggest model; this is a massive cost saver.
  • Prefix / prompt caching — reuse KV state for shared prefixes across requests.
Queueing is not optional

GPUs are finite and expensive, so you can't scale them elastically per-request the way you scale stateless web servers. Demand spikes must be absorbed by a queue with admission control: prioritize by tier (paid > free), shed or slow low-priority load under pressure, and give honest backpressure. A well-run inference service is mostly a well-run queue in front of a fixed pool of accelerators. Autoscaling GPUs is slow (minutes to acquire, cold model loads), so you provision to forecast plus a buffer and let the queue handle the rest.

Reliability specifics for inference

  • Streaming failures mid-generation — if a GPU worker dies at token 200 of 500, you need graceful degradation: retry on another worker (losing progress) or checkpoint. Make generations idempotent by message id so retries don't double-charge or double-post.
  • Timeouts & cancellation — enforce a max generation time; propagate client cancels all the way to the GPU to free capacity instantly.
  • Multi-model / multi-version — you'll run several models and versions at once. Route by capability and roll out new versions gradually (see Deployment).

Capability envelope

Handles

Streaming AI generation at high throughput per GPU; the more you optimize batching & caching, the more requests per card.

Breaks when

Demand spikes past the fixed GPU pool — you can't autoscale GPUs in seconds — and the queue backs up.

Can't do

Scale elastically per-request like stateless web; hold low TTFT under overload without shedding/queueing.

Improve in place first

Continuous batching, paged KV cache, quantization, speculative decoding, model routing, prompt caching, admission-control queue.

Gain over L5 The product becomes ChatGPT — it generates, not just stores and relays.
Trigger → L7Users are global; the speed of light and data-residency law force compute closer to them.
L7 · Going global

Multi-region, edge, and the speed of light

A user in Sydney talking to servers in Virginia pays ~200ms round-trip before any work happens — you can't out-engineer physics. Global scale means putting compute near users, which reintroduces the hardest distributed-systems problem: keeping data consistent across regions.

What moves to the edge

  • Static assets & media — CDN, always. Cheapest, biggest win.
  • TLS termination & connection handling — terminate close to the user; backhaul over warm internal links.
  • Connection servers — hold sockets regionally so the persistent connection is short-hop.

What's hard to move: state

You now choose a data topology, each a point on the consistency/latency triangle:

TopologyIdeaCost
Single-region primaryAll writes go home; regions cache readsSimple; far users have slow writes
Data residency by userEach user's data lives in their home regionFast for them; cross-region chats get complex
Active-active multi-masterWrites anywhere, reconcileFastest; hardest correctness (conflict resolution)
For an LLM product, geography follows the GPUs

Inference must run where the accelerators are, and GPU capacity is scarce and unevenly distributed globally. So the practical pattern is: connections and light state at the edge, inference in a handful of GPU super-regions. You accept some latency to reach the model, and spend the latency budget you saved at the edge on getting the prompt there fast. Data-residency and compliance (GDPR, regional data laws) often force the topology more than performance does.

Capability envelope

Handles

Low-latency worldwide access, regional data residency, and resilience to a whole region failing.

Breaks when

Cross-region consistency conflicts, uneven GPU capacity between regions, or egress costs balloon.

Can't do

Beat the speed of light, or offer strong write-local consistency everywhere at low cost.

Improve in place first

Edge termination, per-user data residency, CDN, async replication, route inference to nearest GPU region.

Gain over L6 The product feels local everywhere and survives regional outages — the top of the ladder.
Beyond L7It's no longer new levels — it's endless refinement: cost, quality, efficiency, and the measurement discipline that follows.
Chapter 02 · Cross-cutting

Authentication & security

Security isn't a level you add at the end — it wraps every request from L0 onward. At scale, the goals are: prove who the user is cheaply on every request, keep sockets authenticated, and contain blast radius when something is compromised.

AuthN vs. AuthZ

Authentication ("who are you") is usually solved with OAuth 2.0 / OpenID Connect (social/enterprise login) issuing tokens. Authorization ("what may you do") is a separate, ongoing check — can this user read this conversation, use this model, spend this quota.

Tokens: the stateless-vs-revocable tension

  • JWT access tokens — signed, self-contained, verifiable by any server without a DB hit. Perfect for a stateless tier. The catch: they're hard to revoke before expiry.
  • Short-lived access + long-lived refresh — the standard fix. Access tokens live minutes; a refresh token (revocable, stored server-side) mints new ones. Revoke the refresh token to cut off access soon.
  • Authenticating the socket — validate the token at connection time, and re-check periodically; a socket open for hours shouldn't outlive a revoked session.
Chat-specific security landmines

Authorization on fan-out: when a message is delivered, re-verify the recipient is actually a member of that room — never trust that subscription implies permission. Injection into the model: in an AI product, user (and retrieved) content becomes part of a prompt — treat prompt injection as an untrusted-input problem; never let model output trigger privileged actions without an authorization gate. Data isolation: one tenant's conversations must never leak into another's context or cache.

Defense in depth

  • TLS everywhere, including internal service-to-service (mTLS / a service mesh).
  • Encryption at rest for messages and attachments; envelope encryption with rotating keys.
  • Secrets in a vault, never in code or env files committed to a repo.
  • Least privilege for every service identity; audit logs for sensitive actions.
  • WAF and DDoS protection at the edge (the front door is the biggest target).
  • End-to-end encryption for human↔human privacy products — note it's largely incompatible with server-side AI features, which must read the plaintext.
Chapter 03 · Cross-cutting

Rate limiting, quotas & abuse

When each request can cost real GPU-seconds, rate limiting stops being about politeness and becomes about survival and unit economics. It's also your first line of defense against abuse and runaway costs.

Algorithms

AlgorithmBehaviorBest for
Token bucketAllows bursts up to a cap, refills steadilyGeneral API limiting — the default
Leaky bucketSmooths to a constant rate, no burstsProtecting a fixed-capacity backend (GPUs!)
Sliding windowAccurate count over a rolling periodFair per-user quotas

Limit on multiple dimensions at once: requests/sec, tokens/minute (the one that actually maps to cost), concurrent generations, and spend/day. Enforce in a shared store (Redis) so limits are global across all app servers, not per-box.

Tiering is the business model

Free, plus, and enterprise tiers get different limits, different queue priorities, and often different models. Under capacity pressure you gracefully degrade the free tier (longer queue, smaller model, "try again shortly") to protect paying users. Rate limiting, queue priority, and billing are three views of the same underlying admission-control system.

Abuse & safety

  • Content moderation — classify inputs and outputs; block or flag disallowed content. This runs on the hot path, so it must be fast (often a small dedicated model).
  • Bot / scraping defense — detect automated abuse that racks up cost; CAPTCHAs at signup, anomaly detection on usage.
  • Cost anomaly alerts — a single account suddenly consuming 1000× normal tokens is either an attack or a bug; alert and auto-throttle.
Chapter 04 · Cross-cutting

Observability

At this scale you cannot debug by reading logs on a box — the box is one of thousands and may already be gone. You instrument the system so it explains itself. The rule: if you can't measure it, you can't operate it.

The three pillars, plus one

  • Metrics — cheap numeric time series: request rate, error rate, latency percentiles, GPU utilization, queue depth, tokens/sec. Alert on these.
  • Logs — structured, sampled at high volume, centralized and searchable.
  • Traces — follow one request across gateway → context builder → queue → GPU → stream. Essential when latency comes from one hop among many.
  • Evals (AI-specific) — for an LLM product, output quality is a first-class signal. Continuously sample and grade responses; watch for regressions when you change models or prompts.

The percentiles that matter

Average latency lies. At 1M req/s, the 1% slowest requests are 10,000 requests per second of unhappy users. Track and alert on p50 / p95 / p99 / p99.9 separately. For chat specifically, the two headline SLIs are time-to-first-token (does it feel responsive?) and inter-token latency (does it stream smoothly, or stutter?).

SLOs turn metrics into decisions

Define Service Level Objectives (e.g. "99.9% of streams start within 1s over 28 days") and an error budget — the allowed amount of failure. When you're burning the budget too fast, you freeze risky launches and fix reliability; when you have budget to spare, you ship faster. It aligns velocity and stability instead of arguing about them.

Chapter 05 · Cross-cutting

Deployment & release strategy

A system that serves millions can never go fully offline to update. Every change must roll out while the system stays up, and roll back instantly when it's wrong. This is where CI/CD, containers, and orchestration earn their place.

The foundation

  • Containers (Docker) for reproducible, identical builds from laptop to production.
  • Orchestration (Kubernetes) to schedule, heal, and autoscale those containers — with GPU-aware scheduling for the inference tier.
  • Infrastructure as code (Terraform) so the whole system is versioned, reviewable, and reproducible.
  • CI/CD pipeline — every commit is tested, built into an image, and promoted through environments automatically.

Progressive delivery

StrategyHowRollback
RollingReplace instances a few at a timeRoll forward/back gradually
Blue-greenFull parallel environment; flip traffic at onceFlip back instantly
CanarySend 1% → 5% → 50% → 100%, watching metricsHalt & revert at first bad signal

Deploying stateful and GPU tiers is different

Connection servers hold live sockets — a naive rolling deploy drops millions of connections. Use connection draining and let clients reconnect (with jittered backoff to avoid a thundering herd). GPU/model rollouts are heavyweight: loading a model onto a fleet takes minutes and capacity is scarce, so you canary new model versions carefully, keep the old version warm for instant rollback, and often route by version so you can shift traffic gradually. Schema changes must be backward-compatible (expand-then-contract): add columns before code uses them, remove them only after all old code is gone.

Chapter 06 · Cross-cutting

Cost & capacity planning

For a normal web app, cost is an afterthought. For an LLM chat product, cost is the architecture — the difference between a viable business and a money furnace often comes down to tokens-per-dollar. Nearly every L6 optimization exists to move this number.

The cost hierarchy, and what to do about each

  • Inference (dominant) — right-size the model per query (routing), batch continuously, quantize, cache prompts and common responses, cap max output length, and reserve/commit capacity for a discount over on-demand.
  • Storage — tier hot→cold aggressively; compress; set TTLs; most history is never re-read.
  • Bandwidth / egress — CDN for media; cross-region egress is a silent budget killer, so keep chatty traffic intra-region.
  • The stateless web/connection tier — comparatively cheap; autoscale it freely.
Unit economics beats absolute cost

Track cost per conversation and cost per active user, not just the total bill. That's what tells you whether growth makes the problem better or worse, and it's the number that decides which free-tier limits and model-routing rules keep the business alive. A feature that's cheap at 10k users can be ruinous at 10M if its cost scales linearly with usage.

Chapter 07 · Cross-cutting

Failure modes & resilience

At scale, failure is not an event — it's a constant background condition. Something is always broken; the design goal is that no single failure is visible to most users. You engineer for graceful degradation, not for the absence of faults.

Design principles

  • No single point of failure — redundancy at every tier; assume any one instance, rack, or availability zone can vanish.
  • Bulkheads — isolate failures so a broken subsystem (say, search) can't sink the core chat path.
  • Circuit breakers — stop hammering a failing dependency; fail fast and shed load instead of piling up.
  • Timeouts & retries with backoff + jitter — never retry instantly in lockstep, or you create a self-inflicted DDoS (thundering herd).
  • Idempotency — every mutating operation carries a client-generated id so retries don't duplicate messages or double-bill.
  • Backpressure — when overloaded, say no cleanly (queue, slow down, shed) rather than collapsing.

Graceful degradation ladder

When the system is under stress, shed capability in order of least harm — a partial product beats an error page:

1. disable typing indicators / presence 2. serve cached / smaller model 3. queue free tier, protect paid 4. read-only history mode 5. honest "at capacity" message
Prove it: chaos & game days

Resilience you haven't tested is a hypothesis. Deliberately inject failures in production-like conditions (kill instances, add latency, sever a region) so you discover the weak links before your users do. The teams that run the most reliable systems are the ones that break them on purpose, on schedule.

import sse from 'k6/x/sse';
import { Trend } from 'k6/metrics';
const ttft = new Trend('ttft_ms', true);

export const options = {                 // ramp to find the knee
  stages: [
    { duration: '2m', target: 200 },     # warm up
    { duration: '5m', target: 2000 },    # push toward the limit
    { duration: '3m', target: 5000 },    # stress
  ],
  thresholds: { ttft_ms: ['p(95)<800'] },  # fail the test if SLO breaks
};

export default function () {
  const start = Date.now();
  let got = false;
  sse.open('https://api.example.com/chat', { method:'POST',
    body: JSON.stringify({ prompt: 'hello' }) }, (client) => {
      client.on('event', () => {
        if (!got) { ttft.add(Date.now() - start); got = true; }
      });
  });
}

The knee, and Little's Law

As you ramp, latency stays flat, then hockey-sticks upward at the knee — that inflection is your real capacity, and you provision to stay left of it. Little's Law (L = λ × W: concurrent-in-flight = arrival-rate × time-in-system) lets you predict it: if each generation takes 4s and you can hold 2,000 concurrently, your ceiling is ~500 req/s per pool. Measure two of the three, compute the third, and you can size capacity without guessing.

Step 8 — Automate it: performance gates in CI

  • Regression gates — run a scaled-down k6 test in CI on every change; fail the build if p95 latency or tokens/sec regresses beyond a threshold. This is the discipline that keeps a system fast over time.
  • Nightly full load tests against staging, with results trended in Grafana so drift is visible.
  • Scheduled chaos (game days) — kill a region on a schedule and confirm SLOs hold.
  • Eval gates — before promoting a new model/prompt, run the golden eval set; block on quality regressions just like latency ones.
Measure production, not just the lab

Load tests tell you what should happen; real users on real networks tell you what does. Always run both: synthetic load + chaos for confidence before shipping, and RUM + live SLO burn-rate alerts to catch what the lab never reproduces. The gap between the two is where your next incident lives.

The one-paragraph summary

Build a real-time chat product in layers: a stateless app tier over a durable, sharded data tier; a connection tier holding persistent sockets, fed by a pub/sub backbone that solves fan-out; and — the part that makes it ChatGPT — a queued, batched GPU inference fleet that streams tokens back over SSE.
